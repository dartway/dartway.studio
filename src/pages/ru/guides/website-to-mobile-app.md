У компании есть мобильный сайт для бронирования. Владелец просит «сделать то же самое в магазинах приложений». До оценки стоит закончить одну фразу: *постоянный клиент откроет приложение, чтобы…* Найти знакомую иконку, показать бронь на входе и перенести запись по дороге — три разные задачи.

| Что нужно клиенту | Какой вариант оценивать первым |
| --- | --- |
| Открывать привычную форму бронирования с домашнего экрана | Устанавливаемое веб-приложение (PWA). Уточните, кто может менять сайт, и проверьте установку на телефонах клиентов. |
| Пользоваться готовыми страницами в приложении из магазина, где есть отдельная мобильная функция | WebView для готовых страниц плюс разработка этой функции. Проверьте переходы между ними, вход в аккаунт и кнопку «Назад». |
| Смотреть, переносить и отменять брони через интерфейс, спроектированный для телефона | Отдельное приложение поверх API системы бронирования. До оценки экранов проверьте, что API поддерживает каждое действие. |

Варианты можно сочетать. Например, приложение получает историю бронирований через API, а раздел помощи открывает в WebView.

## Когда достаточно PWA

Пройдите путь вместе с клиентом: открыть ссылку, добавить сайт на домашний экран, закрыть и вернуться на следующий день. Получится ли найти бронь, не разыскивая письмо и не вводя пароль повторно? Возможно, на этом задача уже решена. Способ установки зависит от браузера и платформы. Для работы без сети отдельно определите, что должно оставаться доступным, и проверьте это в авиарежиме. [Руководство MDN по установке PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

## Почему обёртка на WebView иногда обходится дорого

Допустим, площадка арендует сервис бронирования. Площадка меняет логотип и расписание, а вход, переход к оплате и страницу подтверждения контролирует поставщик. Заложите короткую проверку на iPhone и Android: начать бронирование, перейти к оплате, вернуться в приложение, открыть подтверждение по ссылке из письма. Отметьте, какие сбои может исправить только поставщик. Даже маленькая правка сайта тогда влияет на дату выпуска.

Если нужны магазины, опишите, зачем клиент установит приложение. Apple оценивает самостоятельную пользу приложения по пункту 4.2. У Google Play есть отдельное ограничение для приложений, основная задача которых — открывать чужой сайт в WebView без разрешения его владельца. Согласие владельца сайта закрывает вопрос разрешения. Пользу приложения для клиента ещё предстоит показать. [Правила Apple, п. 4.2](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality) · [Правила Google Play](https://support.google.com/googleplay/android-developer/answer/9899034?hl=en)

## Что проверить до оценки приложения на API

Попросите у поставщика документацию и тестовую среду. Возьмите самое сложное действие первого релиза. Для переноса записи нужно определить клиента, получить его бронь, найти свободное время, изменить запись и показать подтверждение. Что произойдёт, если последний слот уже занял другой человек? Публичное расписание подтверждает только возможность показать свободное время. Для оценки переноса нужна пробная операция, которая действительно меняет бронь у поставщика.

Похожая зависимость встретилась в приложении DartWay для онлайн-школы. Ученик покупал курс на внешней платформе, а уроки открывал в приложении. При возврате оплаты доступ требовалось закрыть. Оба события вошли в разработку, хотя на макете экрана урока их не видно. [Кейс приложения для школы](/ru/work/nda-courses/)

**Что прислать на оценку:** ссылку на мобильный сайт, один путь клиента, целевые устройства и магазины, а также информацию о том, кто управляет сайтом и API. Укажите один результат, который хотите проверить на телефоне. [Бриф на оценку приложения](/ru/guides/fixed-price-app-brief/)
